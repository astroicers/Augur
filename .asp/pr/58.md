# refactor(director): 導播管線收成不依賴 React 的深模組 BroadcastDirector

Closes #58

## 問題

`src/components/MascotPanel.tsx` 1181 行、16 個 `useEffect`、24 行含 `useRef`（實際呼叫 21 個），導播管線整條
住在元件裡：取告警 → 去重 → 套別名 → 門檻過濾 → 組句 → 交給 speaker。它的不變量靠
**effect 的宣告順序**維持，檔內三處註明「宣告順序有意義」／「deps 必須一致」。三條都破得很安靜，
而症狀一模一樣：**永久靜音** —— 告警真的在燒而面板一聲不吭，不留任何錯誤訊息、UI 上沒有跡象。
後續 P9 第二批功能（靜音／值班時段、抖動抑制）都要接進這條管線，在元件裡再加一個 effect
只會讓順序依賴更難維護。

本票把導播收成一個**不依賴 React** 的深模組。**對外行為一律不變**，主要證據是
`MascotPanel.test.tsx` 的 58 條既有斷言**一行未改且全綠**（`git diff` 不含該檔）。

## 做法

新增 `src/director/BroadcastDirector.ts`（300 行，單一檔案）。對外三個函式與一組型別：

| 匯出 | 做什麼 |
| --- | --- |
| `createBroadcastDirector(opts)` | 建導播。**在這裡**（也只在這裡）建立它自己的 source 與 dedup |
| `director.evaluate(input, settings)` | 跑一輪：取告警 → 別名 → 門檻 → 防洪 → 組句 → 交付 sink。回 `BroadcastRound` |
| `director.dispose()` | 收掉（source 與 dedup 一起） |
| `panelAlertSource(panelId, fetchRules)` | 正式的來源層工廠（`createPanelAlertSource` 綁上 panelId 與 fetcher） |
| `windowSecFor(repeatFiringMin)` | `0` → `Infinity`（永不重播）。從元件搬過來，只有一份 |

介面刻意窄到讓單元測試能用假物件驅動：來源只要 `{ evaluate }`（`AlertSource`），
播報器只要 `{ enqueue, pending }`（`BroadcastSink`，是 `Speaker` 的子集）。

**元件這一側**只剩接線：`directorFor(id)` 取（必要時建立）導播，每輪 panel data 餵一次
`evaluate(input, settings)`，拿回的 `items`（時間順序）轉成 feed 行、取 `items[0]` 當表情、
`round.pending` 更新佇列數。四個 effect 收成「一個取用點 + 一個純 cleanup 的卸載 effect」。

### 關鍵取捨一：設定**隨呼叫帶進去**，不是另一個 effect 同步的 ref

原本是 `fallbackSeverityRef` + 一個 `[fallbackSeverity]` 的同步 effect，而它**必須宣告在
導播 effect 之前**（檔內原註解：「**宣告順序有意義**：這個 effect 要排在下面的導播管線之前，
讓 evaluate 讀到的是本次 commit 的值」）。

現在 `evaluate(input, settings)` 把五個設定當參數收下。「改設定後的下一次 evaluate 讀到新設定」
於是不是一條要遵守的規則，而是**沒有別的可能** —— 導播沒有第二個存設定的地方。
`fallbackSeverity` 仍以函式交給來源層（評估當下才讀），所以換這個選項照舊不重建任何東西。

### 關鍵取捨二：導播**刻意不在 effect 裡建立**

在 effect 裡建立就得把它排在評估 effect 之前，否則第一次 commit 時 ref 還是 `null`、
那一輪被整個跳過 —— 那是把剛拆掉的宣告順序依賴原封不動搬回來（這正是檔內 `setReaction`
那條註解記錄的、實作時真的犯過的錯）。改成 `directorFor(id)`「用的時候才取」：
評估 effect 第一件事就是呼叫它，拿到的一定是活的導播，與任何 effect 的先後無關。
卸載時收掉導播的那個 effect **只有 cleanup、沒有 mount 行為**，同樣與宣告位置無關。

### 關鍵取捨三：source 與 dedup 的生命週期合成一個

原本是兩個 effect、兩套 deps，而「deps 必須一致」只能靠註解維持；寫歪一次就留下
「`episodes` 清了而 `lastFiring` 還記得」—— 永久靜音。現在兩者都在
`createBroadcastDirector()` 裡建立、在 `dispose()` 裡收掉，**導播沒有「只重建 source」的入口**，
那個組合建構不出來。`onSupersede` 也在模組內接到自己那份 dedup 上，呼叫端接不接線都不影響。
測試直接釘住 `sourceCreated() === 1`。

### 關鍵取捨四：一輪評估是原子的

原本 `busyRef` 這個並發守門沒有名字也沒有測試。現在它是模組的第 4 條不變量：
設定在 `evaluate()` 進入時定格，非同步鏈還在跑時呼叫端再改設定，也不會讓同一輪的門檻與
組句讀到兩套值；被擋下的那一輪回 `evaluated: false`（與「評估過但沒有要播的事」分開），
而且連來源層都不碰、更不會把設定換掉。

**這是唯一一處刻意的行為收緊**，誠實記下來：舊實作的 `setWindow`／ref 同步是獨立 effect，
評估進行中改選項會被同一輪的非同步鏈讀到（一輪裡兩套設定）。新實作讓那一輪沿用它開始時的設定，
新設定在下一輪生效。沒有任何既有測試涵蓋這條路（兩支相關測試都在 rerender 之間 `await settle()`），
而觀測上的差別只在「選項改動與評估剛好同時」的那一瞬；收緊的方向是讓一輪內部自洽。

### 相依陣列：刻意不含 `repeatFiringMin` 與 `fallbackSeverity`

評估 effect 的 deps 是 `[data, id, minSeverity, alertLang, severityAliasSpec]`（`directorFor` 恆定）。（合併時訂正：原寫「維持」不正確——main 是 `[data, minSeverity, alertLang, severityAliasSpec]`，`id` 與 `directorFor` 是本 PR 新加的，影響見文末〈合併時訂正〉。）
那兩個選項只在 effect **真的跑**的時候才被讀，而那一刻讀的是最新一輪 render 的閉包，
所以不會讀到舊值；放進 deps 只會讓「在編輯面板裡改那兩個選項」各多打一次 rules 端點。
`// eslint-disable-next-line react-hooks/exhaustive-deps` 指的就是這兩個（舊實作的 dedup effect 有同樣的
一行，理由同類）。

## AC-7：是否需要 ADR

**結論：不需要新開 ADR，也沒有任何 ADR-004 的決策被改變。** 依票文明文，本票**不寫 Draft ADR**
（asp-ng 的 `adr-draft` 檢查會擋下整個 commit）。逐條對照 ADR-004 的七條決策：

| ADR-004 決策 | 本票是否改變 | 依據 |
| --- | --- | --- |
| 1. 形態與技術棧（create-plugin／webpack／React 18／`@grafana/ui` 樣式／externals） | ✗ 未改 | 不動 `.config/`、不動 `package.json`／lockfile、零新相依、仍是 webpack 建置；`plugin.json` 一字未動（ID 與 type 不變）。新模組是純 TypeScript，不引入任何執行期相依 |
| 2. 告警來源（`alertState` 當觸發訊號、rules 端點當內容來源；threshold 走 standard field config） | ✗ 未改 | 來源層 `sources/panelAlerts.ts`／`rulesFetcher.ts` 的對外介面一行未改。`alertState` 與 `data.request.dashboardUID` 的取法原封搬運（註解一併搬），`AlertStateLike` 仍由來源層定義 |
| 3. avatar：2D 精靈圖 | ✗ 未改 | 未碰 `src/avatar/` |
| 4. 語音：Web Speech（經 ADR-005 修訂為預設＋降級） | ✗ 未改 | 未碰 `src/speech/`。導播只依賴 `{ enqueue, pending }`，那是既有 `Speaker` 介面的**子集**，不是新契約 |
| 5. 明文繼承 ADR-002 的 `BroadcastPlan` 與 `AvatarController` | ✗ 未改 | `BroadcastPlan` 的欄位與值域不變（仍由 `core/format.ts` 的 `buildBroadcastPlan` 產生）；`AvatarController` 未碰。「導播與呈現之間的純資料邊界」這條界線本票是**強化**而非改變：先前導播與呈現住在同一個元件裡，現在邊界有了檔案形狀 |
| 6. 跨 panel 互動：漸進降級 | ✗ 未改 | 未碰 `src/dom/`，互動層那個 effect 一字未動 |
| 7. 保留與廢除（`src/core/*` 保留、bridge 投遞設定刪除） | ✗ 未改 | `src/core/` 的五支模組對外介面一行未改，導播是它們的**呼叫端**。仍然零後端、零常駐服務 |

為什麼「新增一層目錄」不等於決策改變：ARCHITECTURE 的維護規則把「決策改變」與「動到 seam」
分成兩條，動 seam 的要求是**同步更新資料流圖與檔案表**（本票 AC-6 做的事），不是開 ADR。
本票沒有新 source、沒有新 `AvatarController` 實作、沒有新 panel option、資料流也沒有改向 ——
同一串步驟、同一個順序、同一組輸出，只是換了住的地方。對照 #32／#50 被要求補 ADR 的那兩次：
那是**行為**改變（語音開關是使用者看得到的新功能，寫進了 ADR-007），本票的對外行為一律不變，
機械證據就是 AC-4（58 條既有斷言一行未改且全綠）。

若日後有人認定這一層本身值得一份 ADR（例如要把它寫成「導播層與呈現層分離」的長期約束），
那屬主管層另開 ADR 票的範圍，本票不代寫。

## 合併時訂正（2026-10-15，asp-ng 主管層）

獨立複審判 NEEDS_WORK，指出兩條 MED、三條 LOW。主管層依「reviewer 直接修、全新 verifier 只驗」的做法處理如下：

- **MED-1 已修（行為）**：原本 `dispose()` 只在 `evaluate()` 入口檢查。若 dispose 時正有一輪停在 `await source.evaluate(...)`，放行後仍會把結果交給（已換成新的）播報器。React StrictMode 的 mount → unmount → mount，或 panel id 改變時，同一則告警會被新舊兩個導播各交付一次；main 是靠元件層級的 `busyRef` 擋掉這種情況。修法是在 `await` 之後再查一次 `disposed`。新測試 `不變量4：dispose 時正在 await 的那一輪，放行後不交付、回 evaluated:false`：修前紅、修後綠。這個修法也讓 StrictMode 重掛後的下一次 refresh 不會重念（main 重掛時會重建 dedup），比 main 更穩。
- **MED-2 已修（測試）**：`不變量4：前一輪還沒結束時…不改設定` 原本驗不到「不改設定」——假 source 在 await 之前就讀了 hook。主管層加了一條斷言 `hooks().fallbackSeverity() === 'critical'`。實測把 `applySettings(next)` 挪到 busy 守門之前，這條就會紅。
- **LOW-1 已改**：三條測試名稱改成只寫斷言驗得到的事（上方對照表已同步）。
- **LOW-2 已訂正**：deps 那句、`useRef` 的計數已改正。「唯一一處刻意的行為收緊」與 AC-7 段的「同一組輸出」說得過滿，實際上還有下一條所列的差異。
- **LOW-3（接受，記為已知差異）**：評估 effect 的 deps 多了 `id`。panel id 改變但 data 沒變時，會立刻以新導播評估一次，main 則要等下一次 data 變動；再加上整行停用 `exhaustive-deps`。id 很少改變，影響有限，不擋合併。
