# feat(sources): 以指定 label 當告警名與去重 key——一條總規則底下的每則告警各自播報

Closes #69

## 問題

EKS 的值班牆是**一條** Grafana 總規則，查詢就是 `ALERTS{alertstate="firing"}`
（eks-infra#1210）。卡住的是兩件事疊在一起：

1. Grafana 用**規則名覆蓋**每個 instance 的 `alertname` —— ALERTS 查回的
   Watchdog／KubeletTooManyPods 到 panel 手上全變成同一個規則名。
2. 本面板的告警名取 `labels.alertname`，而**名字就是去重單位**
   （fingerprint 是 `alert:${名字}`）。

結果是一條規則底下不管燒幾則，**只念第一則**，其餘被 dedup 當成同一則吞掉。

查詢端已經有解法：`label_replace(…, "wall_alertname", "$1", "alertname", "(.*)")`
把原名保留成 instance label。panel 只要能指定「用哪個 label 當告警名」就能用。

## 做法

一個新 panel 選項 + 一個純函式 + 一條接線，**沒有新模組**。

| 新增／改動 | 做什麼 |
| --- | --- |
| `alertNameLabel`（文字，預設 `''`） | 用哪個 instance label 當告警名。空字串 = `alertname`（照舊） |
| `alertNameOf(labels, ruleName, nameLabel)`（`sources/panelAlerts.ts`，新） | 逐 instance 取名，**唯一一處**。空選項走的是與原本**逐字相同**的那行運算式 |
| `parseRulesResponse(raw, uid, panelId, alertNameLabel?)` | 多一個選填參數，取名改呼叫上面那支 |
| `RulesFetcher` 多一個選填的第三參數 | 由來源層在**評估當下**從選項讀出後帶進來 |
| `PanelAlertSourceOptions.alertNameLabel`（可給函式） | 與 `fallbackSeverity` 同一招：換選項不必重建 source |
| `DirectorSettings.alertNameLabel?` / `SourceHooks.alertNameLabel()` | 導播**原樣轉給來源層**，不解析也不判斷 |
| `MascotPanel.tsx` | `(options.alertNameLabel ?? '').trim()` 帶進每一輪的設定，純接線 |

取名之後**什麼都不必改**：fingerprint 本來就是 `alert:${d.alertname}`，episode、
部分恢復的差集迴圈、`onSupersede`、dedup 的 resolved 綁狀態全部沿用 —— 名字一分開，
它們自然就是「以每則告警為單位」。這是本票唯一的設計重點，也是改動這麼小的原因。

### 取捨一：留空時**連第三個參數都不傳**

```ts
const args: [string, number, string?] = label ? [dashboardUid, opts.panelId, label] : [dashboardUid, opts.panelId];
const fetched = await opts.fetchRules(...args);
```

看起來多餘（傳 `''` 的結果一樣），但這是 AC-1 的機械保證：既有的接線測試用
`expect(mockedFetch).toHaveBeenCalledWith('dash-1', 7)` 檢查這個呼叫，而 jest 的那個比對
**連參數個數都算**。多傳一個空字串就會讓既有測試變紅，而 AC-1 要的正是「既有測試不改且全綠」。
於是預設路徑被釘在「連呼叫形狀都一樣」的層級，不只是「結果一樣」。

### 取捨二：改了選項 = 舊 episode **被取代**，不是恢復

手上的 episode 是用舊命名規則算出 fingerprint 的。不處理的話，使用者在編輯面板裡填上
`wall_alertname` 的那一刻，那些 fingerprint 不會出現在新一輪的 `detail` 裡 → 掉進部分恢復的
差集迴圈 → 先聽到一句「OncallWall 已恢復」（而告警其實一直在燒），才聽到新名字的 firing。

這正是 `onSupersede` 存在的情境（降級路徑那顆泛用 episode 同一條理由）：刪掉 episode 並請
dedup 一起忘掉，不播恢復句，新名字這一輪就重新建立並照常播一次 firing。
降級路徑的 `alert:panel:N` 不在此列 —— 它的名字固定是「告警」，與 label 無關。

### 取捨三：rules 快取**連 label 一起記**

快取命中條件從「在 10 秒窗內」改成「在 10 秒窗內**且 label 相同**」。不比對的話，剛改好選項的
那 10 秒拿到的還是舊命名的清單，使用者會以為選項沒生效。比對條件寫在 `rules()` 裡，
而不是靠別處記得去 `cache = null` —— 這一條不該變成另一條「靠紀律維持的順序」。

### 取捨四：文件的「選項總數」留著數字，但改成機械比對

`docs/ARCHITECTURE.md` 的維護規則寫著「不要寫死會漂的數字」，而〈設定〉偏偏寫死一個。
AC-6 明文要求「選項總數也要更新」，所以數字留著（15 → **16**），但加了一支測試拿它跟
`setPanelOptions` 的實際註冊數比對，同時逐項比對表格的每一列。加減選項而忘了動文件時這條會紅。

## 票上留言的判讀

留言來自 `asp-ng-supervisor-legacy[bot]`（**非 repo collaborator**，依簡報僅供參考、不是 AC 的
權威來源）。三項建議逐條處置：

- **(a) AC-3 漏了「只有空白」的 label 值 → 建議 trim：採納。** 與票文不衝突（票文只說「不存在或
  是空字串」要退回，沒說只有空白時要留空），而留空白的後果正是本專案連開四票的那一族缺值坑
  （`alert:   ` 的 fingerprint、「偵測到告警：」後面一片空白）。實作在 `alertNameOf`：
  取值後 `trim()`，空字串與只有空白一律退回 `alertname`，非空則用修剪後的值。
  選項字串本身也在兩處 trim（面板讀選項時、解析時），因為編輯器裡貼 label 名很容易帶到空白，
  而帶空白的 label 名永遠比對不中任何 label——症狀是「填了卻完全沒反應」。
  ⚠️ 一個誠實記下的微小偏差：若有人把選項明確填成 `alertname`，而某個 instance 的
  `alertname` 值是 `" Watchdog "`（前後帶空白），現在會念成 `Watchdog`。留空的預設路徑**不經過**
  這段（走的是與原本逐字相同的運算式），所以既有 dashboard 不受影響。
- **(b) 選項總數與 #70／#71 會在同一節打結 → 建議明訂先後或別寫死：部分採納。**
  AC-6 明文要求「選項總數也要更新」，所以數字留著（改成 16），但加了機械比對（取捨四）。
  **留一個合併順序的提醒給主管層**：`docs/ARCHITECTURE.md`〈設定〉的那個數字與表格、以及
  `src/panelOptions.ts`／`src/module.ts`，#70／#71 會動到同幾處；本票之後合併的那張票需要
  rebase 時把數字加上去（新加的測試會讓漏改變紅，不會靜默漂掉）。
- **(c) 釘住「不同規則底下 label 值相同時仍共用 fingerprint」：採納。**
  `#69：不同規則底下 label 值相同時仍共用 fingerprint（key 刻意不含規則名與 panelId）`，
  並在 `panelAlerts.ts` 的 fingerprint 註解寫明這個語意不變。

## 不在本票

票文〈不在本票〉的三項都**沒有**動到：播報紀錄（ADR-006）的念名仍走 `history.ts` 既有的路徑
（本票未改該檔）；「目前數值」能不能關掉未碰；「同一個 alertname 有多個 instance 時只念一次」
的語意在選項留空時完全不變（`#69 AC-1：留空時一條總規則底下的兩則仍共用 fingerprint` 就是
釘它的那支測試），要改它得先動 ADR。
