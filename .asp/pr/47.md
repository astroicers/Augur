### AC-1 — sprite 工具：`[3f]` 的「單一視窗碼面積」對 E／B／M 各實驗一次

`tools/check-sprite-sheets.selftest.mjs` 的 `[3f]` 語意層原本把這條寫在九格的迴圈裡、
條件是 `code === k`：

```js
for (let c = 0; c < CELL_COUNT; c++) {
  const code = m.reactionOwnership[c];
  for (const k of ['E', 'B', 'M']) {
    if (code === k && popcount(C.ownershipMask(k, m)) !== area(rects[k])) { … }
  }
}
```

於是它實際量到幾個碼**完全由測試資料決定**。實交付 manifest 的九格是 `'BMK'`／`'EBMK'`
這類組合碼，`'E'`／`'B'`／`'M'` 三個單碼一個都不在裡面 —— 這條斷言在實交付那一組上
整個空轉，三組 CASES 加起來也只偶然量到幾個。

做法：把它抽成 `singleWindowMismatches(maskOf, label, m)`，對 `['E', 'B', 'M']`
**無條件各問一次**，回傳 `{ mismatches, measured }`。斷言本身一併釘住實量次數：

```js
ok(`單一視窗碼的遮罩面積正好等於該視窗（E／B／M 三個碼 × ${CASES.length} 組 manifest 各實量一次）`,
  bad.win.length === 0 && winMeasured.length === 3 * CASES.length, …);
```

`winMeasured.length === 3 * CASES.length` 是防「條件被改回九格裡去」的那一半 ——
少了它，下一個人把 `if (code === k)` 加回來時這條會**全綠而什麼都沒量**。

**「刻意把 B 窗的遮罩弄錯 → 該斷言轉紅」是常駐斷言，不是手工驗證過一次**：
`maskOf` 可替換就是為了這個。同一節末尾用 `brokenBMask`（只動含 `B` 的碼，把 B 窗
最上面那一列挖掉 —— 可能的最小偏差）再跑一次同一個函式，斷言它**紅且只紅 B**：

```
ok    刻意把 B 窗的遮罩做壞一列 → 上面那條轉紅，而且只紅 B（E／M 維持綠）
```

順帶（同一類缺陷，同一次重構裡成本為零）：隔壁那條 `K 不含 E／B／M 任何一個像素`
原本也綁在 `if (code === 'K')` 上，九格裡沒有單碼 `'K'` 就一次都不跑。一併移出迴圈，
改成每組 manifest 直接問 `ownershipMask('K', m)` 一次。這是**收緊**不是放寬。
`產權碼加一個字母只會放寬不會收緊` 仍留在九格迴圈裡 —— 它量的就是實際交付的那些組合碼，
綁在資料上是對的。

### AC-3 — 跨 panel 偵測：recheck 節流改用單調時鐘

`watchDashboardDom` 的節流窗原本用 `Date.now()` 量：

```ts
if (dom.crossPanel || Date.now() - lastProbeAt < minRecheckIntervalMs) { return false; }
```

牆鐘會**往回跳**（NTP 校正、使用者改系統時間、VM 從 snapshot 恢復）。往回撥一小時，
`now - lastProbeAt` 就變成 `-3600000`，永遠小於節流窗，於是 `recheck()` 一路回 false
**直到牆鐘追回來**。而計時器的有界重試窗（6 秒）過後，`recheck()` 是唯一的升回途徑
—— 卡住就等於永久降級，正是 #44 要修的那個症狀換一個起因復活。

改成 `performance.now()`（同一個 time origin 起算、不受系統時鐘調整影響，差值不可能為負）。
兩處都改：建構時的 `lastProbeAt` 初值與 `probe()` 裡的更新。

測法（`src/dom/__tests__/dashboardPanels.test.ts`，兩條）：只把**牆鐘**往回／往前撥
（`jest.spyOn(Date, 'now')`），單調時鐘照 fake timer 前進。這在本專案的 jest 設定下
真的分叉得開 —— 實測 jest 的 fake timers 連 `performance.now()` 一起接管
（`advanceTimersByTime(1000)` 讓它前進 1000），而對 `Date.now` 的 spy 不會動到它。

- `recheck 的節流用單調時鐘：牆鐘往回撥一小時也不會把它卡死` → 節流窗過後 `recheck()` 回 `true`、升回一次。
- `牆鐘往前跳也不會讓節流窗失效（單調時鐘兩個方向都不受牆鐘影響）` → 牆鐘 +1 小時但
  單調時鐘還在窗內時 `recheck()` 仍回 `false`。這條防的是「改用單調時鐘」被誤讀成
  「把節流拿掉」。

### AC-4 — `stop()` 之後 `recheck()` 一律回 false、不呼叫 `onUpgrade`

原本 `stop()` 只收計時器（`left = 0` + `clearTimeout`），而 `recheck()` **不經過計時器**。
後果：`MascotPanel` 卸載時 `watcher.stop()` 跑過了，但那一拍已排好的 rAF 仍會先
`watcher.recheck()` 才檢查 `hostRef.current`（見 `MascotPanel.tsx` 的 `onMove`）——
能升回，而升回就 `onUpgrade` ＝ 對著已卸載的 React 樹 `setScope`，順便把 listener
重綁回 `document`。

做法：加一個 `stopped` 旗標，並把「收計時器」與「停用 watcher」分開：

- `cancelRetries()` —— 只收計時器。升回時走這條（watcher 功成身退，不是被呼叫端停掉）。
- `stop()` —— `stopped = true` ＋ `cancelRetries()`。
- `recheck()` 的第一個條件就是 `stopped`。

介面文件同步改掉（`stop()` 的語意從「清掉計時器」變成「清掉計時器並永久停用」）。
`probe()` 裡不另設 `stopped` 守衛：`recheck()` 與計時器是通往 `probe()` 的全部路徑，
而計時器已由 `stop()` 清掉 —— 多一道守衛會是一條測不到的分支。

測法（兩條新測試）：

- `stop() 之後 recheck() 一律回 false、不呼叫 onUpgrade（節流窗外、DOM 也真的變了）`
  —— 連問兩次都是 false，證明不是「被節流擋住」而是整條路關了。
- `stop() 在計時器重試窗還沒用完時呼叫：recheck() 也不得把它救回來`。

既有那條 `stop()：計時器清光…` 一字未改（它只驗計時器那一半，仍然成立）。

### AC-5 — emotion 測試的 `beforeEach` 要清掉 `mockReturnValueOnce` 佇列

`src/core/__tests__/emotion.test.ts` 的 `beforeEach` 原本是 `normalizeSpy.mockClear()`
—— 只清呼叫紀錄，**`mockReturnValueOnce` 排進去的佇列會留著**。而檔裡有兩條結構護欄
各排一筆 once 回傳值後立刻消費；只要其中任一條在消費之前就斷言失敗（翻紅會中斷該測試），
那筆冒牌回傳值就留在佇列裡，由**下一條測試的第一次 `normalize` 呼叫**吃掉：一條真失敗
後面跟著一串假失敗，而且被污染的是誰取決於檔案裡的順序。

改成 AC 明文建議的寫法：

```ts
const actualNormalize: typeof normalize = jest.requireActual('../severity').normalize;

beforeEach(() => {
  normalizeSpy.mockReset();                        // 連佇列與實作一起清掉
  normalizeSpy.mockImplementation(actualNormalize); // 把「委派真實實作」裝回去
});
```

第二行是必要的：`mockReset()` 會把實作一起清掉，而本檔的前提是「包裝與真實實作一字不差」
（檔頭），少了它每條測試都會改成在量 `undefined`。

另外補一對**常駐護欄**把這個情境釘住（順序有意義，jest 在同一檔內依宣告順序跑）：

- `佇列外洩護欄（上）：刻意排一筆 mockReturnValueOnce 卻不消費` —— 模擬「前一條中途失敗」。
- `佇列外洩護欄（下）：上一條留在佇列裡的冒牌回傳值不得流到這裡` —— 驗真實行為。

把 `beforeEach` 改回 `mockClear()`，下面那條就紅在
`severityToEmotion('info', 'firing')` 回 `'critical'`（實測，見下表）。
