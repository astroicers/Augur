# fix(sources): 換 alertNameLabel 時只重念名字真的變了的那幾則

Closes #85

## 問題

`panelAlerts.ts` 的 `forgetOnLabelChange()` 只看選項**字串**有沒有變：變了就把手上
**所有**具名 episode 當成被取代、通通忘掉，下一輪整面重念一次。名字其實沒變的那幾則
也一樣會重念：

- 從留空改成填 `alertname`（兩者在 #69 AC-1 是等價的）；
- 沒帶那個 label、本來就退回原名的 instance；
- 在編輯器裡打字打到一半剛好 refresh（例如 ` alertname `）。

不會靜音，但是噪音——#69 合併時把它記成 LOW F2「若要改成只重念名字真的變了的，另開票」。
這就是那張票。

## 做法

一句話：**把「名字變了嗎」的判定，從選項字串搬到換 label 之後的第一份清單上。**

換掉 label 之後，差集迴圈本來就會算一個 `stillFiring`（這一輪仍在燒的 fingerprint，
名字是用**新** label 取的）。手上那些用舊命名算出來的 fingerprint，只要還在這個集合裡，
就代表它的名字根本沒變——episode 照常延續、dedup 照常抑制、不重念。不在裡面的那幾則
才是真的改了名，那些才送 `onSupersede`。

| 改動 | 做什麼 |
| --- | --- |
| `forgetOnLabelChange()` → `noteLabelChange()` | 不再當場刪 episode，只記一個 `pendingRelabel` 旗標 |
| 差集迴圈的取代條件 | 從「只有泛用 episode」擴成「泛用 episode **或** 這一輪換過 label」——而換過 label 的那一輪，能落到這個迴圈的已經是「新清單裡沒有這個名字」的那幾則 |
| `normalizeNameLabel()`（新，export） | 選項字串正規化：修前後空白 + **`alertname` 視同留空**。`nameLabel()` 與 `parseRulesResponse()` 共用它 |

**沒有新的狀態要維護**：`episodes` 自己就是那份「fingerprint → 名字」的記錄，生命週期沿用
既有的（恢復就刪、取代就刪、`resolvedAll()` 清空、source 被丟掉就跟著走）。本票只多一個
boolean 旗標。這一點正是留言 (b) 擔心的事，見下方〈票上留言的判讀〉。

### 取捨一：旗標在**對帳的那一輪**才清掉，不是偵測到換值的那一刻

換 label 的那一輪可能走降級路徑（rules 端點掛了、或 `dashboardUid` 還沒到 → `detail` 是空的，
函式直接 `return`）。那一輪手上**沒有**任何用新 label 取好名的清單可以對，若當場把旗標清掉，
下一輪就會把舊命名的 episode 當成恢復、念出一句假的「OncallWall 已恢復」——正是 #69 當初
要擋的那件事。所以旗標留到真的拿到一份新清單時才消費。
測試：`#85：換 label 的那一輪取不到細節時，對帳留到真的拿到新命名的清單那一輪（中間不念假的恢復句）`。

### 取捨二：`alertname` 正規化成空字串（AC-1 明文允許的那條路）

填 `alertname` 與留空在 `alertNameOf()` 裡本來就幾乎等價（#69 AC-1 已釘住解析結果），但
「幾乎」不夠：label 名只要在字串上不同，`noteLabelChange()` 就認定使用者換了取名規則，
`rules()` 的快取鍵也跟著失效。於是這個**什麼都沒改變**的動作會多打一次端點、再讓所有具名
episode 跑一趟取代與重建。正規化之後，那一輪連「換過」都偵測不到（而且快取照樣命中）。

刻意**不**折大小寫：Prometheus 的 label 名區分大小寫，`Alertname` 是另一個 label。

誠實記下的微小偏差（與 #69 判讀 (a) 記的那一條是同一族，方向相反）：若有人把選項明確填成
`alertname`，而某個 instance 的 `alertname` 值是 `" Watchdog "`，#85 之前會念成 `Watchdog`
（走 `alertNameOf` 的 trim），現在會念成 `" Watchdog "`（走與留空逐字相同的那行）。
AC-1 要的就是這兩種寫法等價，而留空才是預設路徑，所以往預設那一側收斂。

### 取捨三：換 label 的**同一輪**剛好恢復的那一則，仍然算「被取代」

手上只有一份**新命名**的清單，所以「它改名了」與「它這一刻恢復了」分不出來，一律當成取代——
也就是少念那一句恢復。這與 #85 之前的行為相同（那時候是整面都當成取代、一句恢復都不念），
所以不是退步，但也不假裝不存在：程式註解、`docs/ARCHITECTURE.md` 與下面的 AC-2 對照都寫明了，
並用一支測試把它釘住（含一個「沒換 label 時照常念恢復」的對照組）。

要分辨就得把每個 instance 的 labels 一路帶到這一層、讓來源層能用**舊** label 再算一次名字，
而那會改 `RuleDetail` 的形狀（或多一次端點呼叫）——兩者都會讓既有測試的 `toEqual({...})` 與
`toHaveBeenCalledWith(...)` 變紅，與 AC-4 的「既有 #69 測試一行不改」直接衝突。因此不做。

## 票上留言的判讀

留言來自 `asp-ng-supervisor-legacy[bot]`（**非 repo collaborator**，依簡報僅供參考、不是 AC 的
權威來源）。兩項建議逐條處置：

- **(a) AC-1 一併 trim（` alertname ` 會被當成不存在的 label，整面重念）：採納。**
  正規化就是「trim 之後再與 `alertname` 比」，所以 ` alertname `、`alertname`、`''` 三者在
  **同一行運算式**上是同一個值。與 #69 的取名 trim 對齊（`MascotPanel.tsx` 讀選項時也還是會 trim
  一次，兩處一致）。測試用 `'  alertname  '` 直接驗這個場景。
- **(b) 保存上一輪 fingerprint → 名字的映射會無限增長，建議比照 #84 AC-4 補生命週期要求：
  不需要，因為本實作沒有建立那份映射。** 判定依據是差集迴圈本來就在算的 `stillFiring`，
  而「上一輪的名字」就是 `episodes` 的 key——那份 Map 的生命週期是既有的（恢復刪、取代刪、
  `resolvedAll()` 清空），本票一個 entry 都沒多加。本票唯一的新狀態是一個 boolean
  （`pendingRelabel`），而它在對帳的那一輪與 `resolvedAll()` 都會被清掉。
  長開的 dashboard 不會累積任何東西。

## 不在本票

- `MascotPanel.tsx`（票文明文不改）與導播：兩者本來就只是把選項字串原樣往下帶。
- 播報紀錄（`sources/history.ts`）的取名：它不持有 episode、沒有「換 label 要不要重念」這回事，
  整份紀錄每次重讀重算。`historyAlertNameOf` 因此**沒有**跟著做 `alertname` 正規化——
  紀錄端填 `alertname` 與留空的差別只在「annotation 的 `{labels}` 段剛好有 `alertname=` 時
  會改讀它」，與本票要消除的重念噪音無關。兩側仍然同名（#70 AC-5）：Grafana 會用規則名覆蓋
  每個 instance 的 `alertname`，所以紀錄端那一步讀到的就是規則名，與播報端走留空路徑的
  `labels.alertname ?? 規則名` 是同一個值。真要把正規化也搬過去是另一張票。
- 「名字相同就共用 fingerprint」的既有語意（跨規則亦然）未動。

## 驗收後的手動確認

本工作容器沒有 Grafana（`npm run server` 需要 docker），所以**現場確認留給 EKS 那側**：
在值班牆 panel 上把 `alertNameLabel` 從空改成 `wall_alertname`，確認只有名字真的變的那幾則
重念、沒帶那個 label 的那幾則一聲不響；再把它改成 `alertname` 來回切，確認完全沒有聲音。
