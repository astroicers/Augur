# feat(director): 靜音時段內破靜音念過的 critical，恢復時也念

Closes #84

## 問題

`quietAllowCritical` 開著時，值班靜音時段內只有 critical 的 **firing** 破得了靜音
（`BroadcastDirector.ts` 的 `breaksQuiet`）。恢復句一律被擋下、只被 dedup 收下。
半夜被 critical 叫醒的人因此永遠聽不到「它恢復了」，只能起身去看螢幕
（#63 自己記下的取捨）。PM 裁定反轉這一條：**念過的 firing，恢復時也要念**；
沒破過靜音的告警恢復時照舊不念。

## 做法

導播多記一份 fingerprint 的集合：「**這一段**靜音時段內破了靜音、而且**真的交到播報器**」。

| 新增 | 做什麼 |
| --- | --- |
| `QuietBreakLog`／`createQuietBreakLog()`（`BroadcastDirector.ts` 匯出） | 破靜音記錄：`remember`／`has`／`forget`／`clear`／`size`。與 `createFlappingTracker` 同一種形狀的工廠 |
| `QUIET_BREAK_LIMIT = 256`（檔內私有） | 記錄筆數上限的 backstop，滿了丟最舊的一筆（`Set` 保留插入順序） |
| `breaksQuiet(item, settings, aliases, quietBreaks)` | 多收記錄；`resolved` 改成「記錄裡有這個 fingerprint 就破得了靜音」 |

接線（都在 `createBroadcastDirector` 內，與 dedup／抖動狀態同生同死）：

```
evaluate()  判斷 quiet → !quiet 或功能關掉 → quietBreaks.clear()   ← 排在「這一輪無事」的早退之前
            交付閘門   → breaksQuiet(…, quietBreaks)
            sink.enqueue() 之後 → firing: remember(fp) / resolved: forget(fp)
onSupersede → dedup.forget + flapping.forget + quietBreaks.forget
dispose()   → dedup.close + quietBreaks.clear
```

### 鍵是**實際交付**，不是 `breaksQuiet()` 的判定

票上留言 (a) 點到的分岔，實作採用它（也是 AC-1 票文字面的「破了靜音**而被念出**」）：
ADR-007 的每瀏覽器靜音排在交付之前，觀看者自己按了靜音鈕時，那則 critical 的 firing
判定得出「破得了靜音」卻一句都沒出聲。若以判定為鍵，那台瀏覽器會記下「念過了」，
解除靜音後冒出一句沒有前文的「已恢復」，而同一面牆上沒按靜音的那台行為還不一樣。
寫入點因此排在 `sink.enqueue()` **之後** —— 沒有播報器、每瀏覽器靜音這兩道整輪的早退
都走不到那裡。兩種情形各有一支測試。

### 恢復側**不另外看嚴重度**

記錄的語意是「我們把你吵醒了」，不是「它現在是不是 critical」。照恢復當下那一則的
severity label 再判一次的話，同一個 episode 中途改標籤就會讓結局無聲無息地不見。
嚴重度門檻那一側不受影響（`resolved` 本來就不受門檻影響，#39 起的既有規則）。

### 清空排在「這一輪無事」的早退**之前**

時段是被**時鐘**跨出去的，不是被告警跨出去的。清空若排在 `items.length === 0`
的早退之後，白天每一輪都無事（最常見的情形）就一次都不會清，昨晚念過的那則 critical
撐到今晚才恢復時會破今晚的靜音 —— 正是 AC-4「不得殘留到下一段時段」要擋的事。
測試用一輪**沒有任何告警**的白天輪次走這條路（`h.run([], ALLOW)`）。

### AC-3 的取捨（票文要求寫明）

**維持現行規則：時段外念出的 firing，在時段內恢復時不念。** 理由：本票的語意是
「被叫醒的人該聽到結局」，而中午聽到告警的人沒有被叫醒；為了那一句在半夜出聲，
代價與收益不成比例。實作上這條是免費的 —— 記錄只在時段內累積（每一輪一離開時段就清），
所以「時段外念出」從來不會進記錄。

若主管層判斷應該念，改動不大（把寫入條件從「本輪在時段內破靜音」放寬成「本輪有實際交付」），
但得先裁定**記錄要往回追多久**：永久保留等於把記憶體綁在 fingerprint 的壽命上，
而「上週念過、今晚恢復」要不要破靜音是另一個問題。建議另開票，不在本票擴張。

### AC-4 的 dispose 這一條怎麼驗

`dispose()` 之後導播永久回 `BLOCKED_ROUND`，而導播**不開內部狀態的後門**
（dedup 與抖動狀態同樣沒有），所以「清掉了沒有」從外面觀察不到。驗法分兩段：

1. `createQuietBreakLog()` 做成匯出的工廠，`clear()`／`forget()`／上限在
   `quietHours.test.ts` 直接驗（與 `createFlappingTracker` 在 `flapping.test.ts` 同一個做法）。
2. 「`dispose()` 真的呼叫了它」以**原始碼比對**釘住（測試名直說它只驗得到原始碼），
   與檔尾那支 import 清單的既有測試同一種手法。

另外三條出口（離開時段／功能關閉／`onSupersede`）都是行為測試，不靠原始碼比對。
`onSupersede` 那支刻意讓新 episode 以 `warning` 再燒起來 —— 否則 `dedup.forget()`
會先把恢復句吞掉，測到的就不是記錄這一面。

### AC-5 的例外：一支 #64 測試的斷言跟著新語意改了

`#64：抖動抑制在靜音閘門之前 —— 兩者同時成立時標記是 flapping，quietAllowCritical 也救不回來`
原本斷言前六輪只念出三句 firing（第 2／4／6 輪的 resolved 被標 `quiet`）。本票之後，
那三則 resolved 的 firing 都是「破靜音念出來過」的，所以恢復句照 AC-1 也念 ——
斷言改成六句（`['firing','resolved',…]`），第 6 輪不再有 `suppressed`。

- 這**不是放寬斷言**：期望值變多、仍是逐項相等比對；該支真正要釘的事（第 7 輪被抖動抑制
  擋下、標 `flapping`、不出聲）一字未動。
- 它用的是 `quietAllowCritical: true`，不在 AC-5「留空或為 false」的保護範圍內。
- 同一段裡不帶 `quietAllowCritical` 的那支（`#64：抑制中的一則落在靜音時段內、而且破不了靜音`）
  一行未改、仍綠，兩個標記的競爭仍有測試守著。
- 行為上的意思：時段內一則正在翻的 critical，在達到抖動門檻之前會念出 firing 與 resolved
  兩側；達到門檻之後兩側都安靜。噪音的上界由抖動抑制管，不由靜音閘門管。

  沒改任何 DOM 結構或語音層，e2e 覆蓋的面不在改動半徑內。
- **`tools/asp-test.sh` 在本容器跑不起來**（`jq` 不存在，腳本第一步就退出），
  所以沒有產出 `.asp-test-result.json` 痕跡檔。判定依據是直接跑 `npm run test:unit`
  的輸出（25 suites / 650 tests 全綠），貼在上一節。
- **沒有在真的 Grafana 面板編輯器裡看過這顆開關的新說明**（同上，沒有 docker）。
  註冊面以真的 `PanelOptionsEditorBuilder` 在 jest 裡驗。
- **QA 回合修掉一處缺陷（AC-2）**：原本「消除記錄」那一側也排在 `sink.enqueue()` 之後，
  所以恢復句被 ADR-007 的每瀏覽器靜音（或「那一刻沒有播報器」）擋下時那一筆不會被消掉 ——
  而它不會再回到靜音閘門（dedup 已經收下），fingerprint 又不含 severity
  （來源層是 `alert:${名字}`），於是同一個名字之後那個**只有 warning** 的 episode
  恢復時會拿這張過期的通行證破靜音，使用者聽到一句從沒聽過前文的「已恢復」，違反 AC-2。
  修法：**消除**那一側移到閘門上（拿到通行證就消），**寫入**那一側仍然等實際交付，
  兩側刻意不對稱；退化方向是「少念一句」。補上兩支回歸測試（靜音鈕／沒有播報器各一支），
  兩支在修改前都會紅。

- **跨時區／日光節約的既有代價不變**：時段判斷仍用每個觀看者瀏覽器的本地時間，
  所以「同一段時段」在不同時區的兩台瀏覽器上是不同的絕對區間，記錄也各自獨立
  （記錄本來就住在各自的導播實例裡）。這是 #63 就記下的取捨，本票沒有加深也沒有改善。
