# 精靈圖素材產製與交付 SOP

> **對象**：實際畫圖的人（自繪或委外）、以及驗收並把素材入版控的人。
> **規格權威**：`sprite-sheet-spec.md`。本檔是**照著做的順序**，不是規格本身。
> 兩者衝突時以規格為準，並回報本檔該改哪裡。
> 最後更新：2026-09-30（對齊三輪工具大修後的現況；先前照本檔畫的眨眼格會被機械退件）。

---

## 為什麼這份 SOP 存在

這套素材有兩個特性，讓「先畫再說」的代價特別高：

1. **改一個比例就是 18 格全部重畫。** 所有格子共用同一個 master frame，
   錨點動了就全部要重來。
2. **出處不明就進不了版控。** repo 是公開的 Apache-2.0，`docs/asset-provenance.md`
   的規則是「出處不明一律不進版控」。畫完才發現授權填不出來，等於白畫。

所以這份 SOP 的順序是刻意的：**該凍結的先凍結、該查的先查完，才開始畫。**

## 階段 0 — 三個必須先完成的前置

三件事沒做完就不要進入階段 1。它們彼此獨立，可以並行。

### 0.1 ~~視線參數盲測~~ —— **已廢除（2026-09-20），不再是前置**

跑了三輪共 98 題，最後證偽的不是某個候選值，而是**整個參數化的前提**。
規格原本要凍結「虹膜直徑」與「瞳孔位移」，隱含假設是這些圖由參數生成；
但規格自己的裁定是**由人用分層繪圖軟體畫**，而沒有畫師會設定 `dy = 0.028` ——
他們畫「往左下看」，然後那張圖讀得出來或讀不出來。

**所以視線可讀性改為交付時的驗收條件（規格 SP-V.1），不是動工前要凍結的參數。**
完整的證偽過程在規格的〈可讀性實測：三輪，與它們證偽的東西〉。

**三輪留下的一件事，寫進階段 2 的 brief**：
水平方向三輪從來沒有讀錯過，錯誤幾乎全部集中在有垂直分量的方向、尤其往下。
這與刺激圖的畫法無關，三輪一致。**往下的三個方向要特別花心思。**

## 階段 1 — 凍結

階段 0 全部完成後，把定案的數值寫回 `sprite-sheet-spec.md` 的對應條文，
並在檔頭把狀態由「尚未凍結」改為「已凍結 YYYY-MM-DD」。

**凍結的意思**：以下數值之後**不得修改**，改了就是 18 格全部重畫。

- 格邊長 S、頭高、眼線 Y、瞳距、嘴中心 Y、肩線 Y
- 眼窗 E、眉窗 B、嘴窗 M 的範圍
- 裁切構圖（胸上／腰上／全身）

~~虹膜直徑、瞳孔位移 `dx` / `dy`~~ **【2026-09-20 移出凍結清單】** ——
它們不再由規格指定（SP-2.6／SP-3.3 已廢除）。虹膜大小與瞳孔怎麼移是畫師表現視線的手段，
驗收看的是結果（SP-V.1 的方向辨識盲測），不是手段。
與本檔階段 0.1 的廢除公告一致。

**未凍結、之後仍可調的**：顏色、線條粗細、描邊、單格內的筆觸細節。

## 階段 2 — 發包 brief

畫的人不需要讀整份規格。從規格摘出這些給他：

1. **凍結後的比例表**（以格邊長 S 為單位，不要給絕對像素）
2. **18 格的內容表**：9 方向 + 9 反應各是什麼
3. **圖層結構要求**（見下方階段 3）
4. **交付格式**：PNG-32、非交錯、透明背景
5. **一句必須講清楚的話**：**角色的頭在 18 格之間不得有任何位移、轉動或縮放。**
   方向感全部由瞳孔位移、眼瞼形狀與睫毛承擔。
6. **驗收條件（SP-V.1）**：128px 下的方向辨識盲測，整體 ≥85%、單一方向不得低於 60%。
   **怎麼達成由畫師決定** —— 瞳孔位移、眼瞼形狀、睫毛、虹膜大小、眼型比例都是他的手段。
   （盲測工具固定**每個非中央方向 10 題、共 80 題**；別用 4 題湊 —— n=4 時
   60% 的門檻會被量化成 75%，真實力 75% 的合格稿有約四分之一機率被誤退。）
6b. **色彩／描邊／邊緣的硬數字**（機械驗收直接紅的，一項都不能漏；
   數值以 `sprite-manifest.example.json` 為準）：
   - 外緣描邊：寬 **0.016·S ±0.002·S**、亮度帶 **0.18–0.24**（工具另有 ±0.03 的
     量測寬容；參考色 `#6E7681`）。若在 manifest 宣告 `stroke.colour`，
     實際墨色要在宣告值 **±12/通道** 內。
   - **剪影邊緣要有 ≥2px 的 alpha 漸層**（SP-2.14）——1-bit 硬邊直接硬失敗。
     **反應格的修補塊邊緣也一樣要羽化**，不是只有外輪廓。
   - **SP-2.15 alpha bleed**：半透明與透明像素的 RGB 必須等於最近不透明像素的
     RGB（匯出時開 bleed / 不要讓軟體填黑）。驗收只有 **warn**（`SP-2.15/未做色彩擴張`，
     2026-10-02 起）：Chromium 縮放前先預乘 alpha，實測看不出差別；不預乘的縮放器上會以黑邊現形。
   - 亮度夾制：剪影內大面積色塊的相對亮度落在 **[0.047, 0.61]**；
     膚色指定 `#E2C8B1`。
   - 線稿最小寬度 **0.020·S**（SP-2.16）；三層留白見 SP-2.1。
7. **一句實測得來的提醒**：三輪盲測共 98 題，水平方向**從來沒有讀錯過**，
   錯誤幾乎全部集中在往下的三個方向（↙↓↘）。那是最容易失敗的地方，值得多花時間。

**委外的話**：brief 之外還要取得**書面的著作權讓與或授權書**，
否則 `asset-provenance.md` 一樣填不出來。行情參考 USD 50–150
（`live2d/_archive/DEPRECATED.md` 記載）。

## 階段 3 — 產製

### 3.1 唯一的真實來源是一個分層原始檔

不是 18 張獨立的圖。所有格子都從**同一個分層原始檔**切圖層匯出。
18 張獨立母檔會重新引入漂移的可能，而整套設計的前提就是「對齊在構造上成立」。

### 3.2 必要的圖層

**眼睛必須拆到這個細度**，否則做不出 9 個方向：

- 眼白（sclera）
- 虹膜（iris）
- 高光（highlight）
- 上眼瞼、下眼瞼
- 睫毛

其餘必要圖層：眉、嘴、記號（汗滴／陰影／怒氣／閃光）、頭髮、身體、斗篷。

⚠️ **`.claude/skills/image-layer-split` 的 `live2d-character` preset 做不到這件事** ——
該 preset 自己的 notes 寫明「眼睛細件與共用 overlay 不在此 preset」，`eye_l` 是
「iris, eye white, eyelid and lashes **together**」一整顆。
它只能當身體／頭髮／斗篷粗胚的起點，**眼睛無論如何都要手工細分**。

同理 `assets/layers/` 的 6 張是另一支工具的**顏色分群**輸出，不是解剖部件；
`live2d/_archive/layerwork/layers/` 是空目錄。這兩者都不能當起點。

### 3.3 四層疊合的產製規則

這是整套設計的核心，**照做則對齊誤差是 0，不照做就回到容差問題**：

1. 先畫 **master frame** —— 完整的角色，表情畫成 calm（`MouthForm +0.2`）。
2. **directions 9 格**：每一格都從 master frame 複製，**只編輯眼窗 E 之內**。
   眼窗之外必須與 master frame **逐像素相同**。
3. **reactions 9 格**：每一格都從 master frame 複製，**只編輯該格對應的視窗之內**
   （表情格改眉窗 B、嘴型格改嘴窗 M、眨眼格改眼窗 E）。
   ⚠️ **匯出前把視窗之外的全部像素抹除／關閉全部底圖圖層**（SP-5.2 步驟 4、SP-5.4）——
   reactions 是**只含修補塊的透明圖**，不是整張立繪。
   照舊句「視窗之外與 master frame 逐像素相同」交付整張立繪，
   會被 SP-7.4/視窗產權九格全紅退件。編輯時對著 master 對位、匯出時只留修補塊。
4. 覆蓋格的**非零 alpha 必須落在 master frame 的臉部皮膚遮罩之內** ——
   視窗是外框上界，不是必須填滿的區域。畫成矩形修補塊會在髮際線外側刷出膚色。

### 3.4 reactions 的格位配置

| 格 | 內容 | 由什麼驅動 |
|---|---|---|
| 0 | click 反應 | `setReaction('click')`，420ms 後自動回復 |
| 1 | warning | `setEmotion('warning')` |
| 2 | critical | `setEmotion('critical')` |
| 3 | resolved | `setEmotion('resolved')` |
| 4 | 嘴半開 | `setMouthOpen`，`charLength < 4` |
| 5 | 嘴大開 | `setMouthOpen`，`charLength >= 4` |
| 6 | 眼全閉 | 眨眼序列中段 |
| 7 | 眼半閉 | 眨眼序列頭尾 |
| 8 | pending | `setReaction('pending')` |

**calm 不佔格** —— master frame 本身就是 calm，calm 狀態定義為覆蓋層不顯示。

## 階段 4 — 機械驗收

交付當下就跑，不過就退回重畫。**每一項都要有明確的通過／不通過，不接受目視判斷。**

**第 0 步（沒做這步 = 沒驗收）**：把 `docs/sprite/sprite-manifest.example.json`
複製到 `src/img/sprite/sprite-manifest.json`，填完所有 `TBD`
（iris / hair 的實際色值、兩張 PNG 的 sha256）。
⚠️ 驗收腳本以**這個檔案存在與否**當開關（SP-7.14）：沒有它，
檢查印 `SPRITE-CHECK: NOT-DELIVERED` 並回 0 —— 素材會**未經任何驗收**入版控，
而且一路綠燈、沒有任何錯誤訊息。

**然後跑一支指令**（腳本存在已久，本檔先前寫「還沒寫」是過期資訊）：

```bash
node tools/check-sprite-sheets.mjs     # 或 npm run check:sprites
```

它跑的是規格 SP-7.1–SP-7.8 的整套（現行 **48 個檢查 id**），
下表只是**最常紅的族群**，不是全集 —— 全集以工具輸出為準：

| 族群 | 在驗什麼 |
|---|---|
| 格式與衛生（SP-7.1、SP-2.14） | 尺寸/PNG-32/非交錯；**剪影邊緣 ≥2px alpha 漸層，1-bit 硬邊硬失敗**；重複格；預乘 alpha / matte 指紋 |
| 頭部不動（SP-7.2） | directions 各格對 master 相減，差異像素必須全部落在眼窗 E 內 |
| 視線綁定（SP-7.3） | 瞳孔位移方向逐格正確、虹膜成形、眼窗無雜塊 |
| 覆蓋層產權（SP-7.4、SP-6.6） | 完全不透明的出界像素 = 0；羽化帶允許溢出「量到的羽化寬度」內 |
| 眨眼（SP-7.4 眨眼系列） | **不是**「輪廓內完全不透明」（那條已廢）——現行是：內縮羽化後的核心裡讀得出虹膜的像素 = 0、核心平均 alpha ≥98%。**修補塊邊緣照樣要羽化** |
| 錨點與幾何（SP-7.5） | 瞳距、兩眼等高、臉中軸 |
| 亮度與描邊（SP-7.7） | 亮度夾制 [0.047, 0.61]；描邊寬 0.016·S ±0.002·S、九格一致 |
| 體積（SP-7.8） | 每張 ≤ 900 KB、合計 ≤ 1.2 MB（pngquant 後；超標先降 S=384，不改比例） |
| sha256（SP-7.15） | 兩張 PNG 的雜湊與 manifest 相符（換圖要一起改 manifest） |

**PASS 也會帶約 19 項「首版僅記錄」的 warn**（覆蓋率、可讀性等
未經真素材校準的門檻）—— 那是給校準用的資料，不是退件理由。

**方向可讀性（SP-V.1）是唯一的人工項**：`npm run blindtest`，128px、
`#181b1f` 底、**每個非中央方向固定 10 題（共 80 題）**：
整體 ≥85%，且沒有任何單一方向低於 60%。「不確定」計為答錯。

**為什麼要加「單一方向不得低於 60%」**：整體 85% 可以由
「七個方向全對、一個方向全錯」達成，而那個全錯的方向在真實使用中就是永遠讀不出來。

**頭部不動與覆蓋層產權是這套設計的全部保障** —— 它們取代了「對齊到 2px 以內」
這類容差檢查。通過它們，對齊誤差在代數上是 0。

> ⚠️ **2026-09-20 修正**：原本這裡寫「先把 `'tools/**'` 加進 eslint 的 ignores，
> 因為 `ecmaVersion` 是 2019、`?.` 與 `??` 會是 parse error」——
> **那個斷言從未被實測，而且是錯的**（實測 `npx eslint --stdin
> --stdin-filename tools/probe.mjs` 對 `a?.b ?? 2` 回 exit 0）。
> **不要加 ignores** —— 加了等於讓手寫 PNG 解碼器失去唯一的靜態檢查。

## 階段 5 — 出處登錄

驗收通過之後、進版控之前。

在 `docs/asset-provenance.md` 的「進版控的資產」表補上新的列，
**四欄都要填滿**：路徑、內容、出處、授權。

「出處」欄要寫得讓**一個陌生人能自己複驗**：誰、用什麼工具、什麼時候。
若涉及生成式服務，條款結論與一級來源 URL 要逐字寫在這裡，不是寫在別處。

**填不出來就不要進版控。** 這條規則是這份文件自己訂的，
而 `live2d/_archive/nami/` 那 36 檔就是沒守它的代價 —— 事後要改寫 git 歷史才清得掉。

## 階段 6 — 進版控

順序不能換（ASP 提交閘的要求）：

```
1. 把素材放進 src/img/sprite/
   —— 必須在 src/ 底下，copyFiles 以 src 為 copy context
2. git add -A
3. bash tools/asp-test.sh          ← 最後一個動作是寫測試痕跡
4. git commit                       ← 立刻，中間不要插入任何 git 指令
```

⚠️ **這四步不能串在同一次指令裡。** 提交閘是 PreToolUse，在整條指令執行**之前**就判定，
串成一行時它看到的是上一次提交之後的狀態，必被擋。

⚠️ `git status` / `git diff` 會刷新 `.git/index` 的 mtime，插在第 3 與第 4 步之間會讓閘門失效。

## 階段 7 — 實作 SpriteController

素材進版控後才做。實作契約在 `sprite-sheet-spec.md` 的〈SpriteController 實作契約〉一節，
重點：

- 檔案切三支：`spriteSheet.ts`（純計算、可測）、`spriteAssets.ts`（只做 import）、
  `SpriteController.ts`（渲染與時序）
- **重用** `gaze.ts` 既有的 `cellToBackgroundPosition`，不要複製一份
- **不要**新增 `src/images.d.ts` —— `.config/types/bundler-rules.d.ts` 已有
  `declare module '*.png'`，再加一份會得到 `TS2300` 並弄紅提交閘的第一項
- 載入或幾何驗證失敗時**退回 `DiagnosticAvatar`** 並顯示降級原因 ——
  沿用 ADR-004 決策 6「壞掉時少一個功能，不是整個 plugin 炸掉」
